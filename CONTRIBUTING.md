# Contributing

Bug reports, feature requests, and pull requests are all welcome. This page is the front door; the detail lives in [`docs/contributing/`](./docs/contributing/).

## Reporting a bug

Open a [bug report](https://github.com/oekeur/zotero-linked-mindmaps/issues/new/choose). Before you do, check that "Zotero Linked Mindmaps" actually appears under Tools -> Plugins. A plugin that fails to load does so quietly, with no error dialog, and that accounts for most reports that turn out not to be bugs.

Attach debug output where you can: Help -> Debug Output Logging -> Enable, reproduce the problem, then View Output. The plugin writes no log file, so that panel is usually the only signal available.

If your mindmaps vanished, read [plugin data recovery](./docs/user-guide/plugin-data-howto.md) first. Trashing the plugin data item hides every mindmap in that library until you restore it.

## Requesting a feature

Open a [feature request](https://github.com/oekeur/zotero-linked-mindmaps/issues/new/choose) and check [ROADMAP.md](./ROADMAP.md) first. The part worth writing carefully is what you tried instead, and why tags or related items fell short.

## Setting up

[Development setup](./docs/contributing/development-setup.md) goes from a fresh clone to a running Zotero with the plugin hot-reloading. You need a local Zotero 7 install and a dev profile separate from the one holding your real library.

```sh
cp .env.example .env
# set ZOTERO_PLUGIN_ZOTERO_BIN_PATH and ZOTERO_PLUGIN_PROFILE_PATH
npm install
npm start
```

`npm install` runs `husky`, which installs the `pre-commit` and `commit-msg` hooks. Commit without those in place and Prettier, ESLint and commitlint never see your work.

From there, [npm-scripts-reference.md](./docs/contributing/npm-scripts-reference.md) lists every script, and [testing-howto.md](./docs/contributing/testing-howto.md) covers running the suite against a live Zotero.

## Before you open a pull request

Run the verification gate:

```sh
scripts/verify.sh
```

It runs build, lint, and a live-Zotero startup check, cheapest stage first, and reports every stage that failed rather than stopping at the first. `--no-test` stops before Zotero is launched; `--test-only` runs the live stage alone. You can run it with a dev Zotero from `npm start` open: the live stage kills its own process group rather than every Zotero it can find.

**If your change touches XUL, Cytoscape, or the live Zotero API, drive it manually as well.** None of that surface is unit-testable here, and its failures are silent rather than thrown: no exception, no console error, just a panel that doesn't render or a plugin that never loads. Run `npm start`, exercise the change, confirm the plugin still lists under Tools -> Plugins, and check Debug Output for "Error running bootstrap method".

Changing `package.json` or `addon/manifest.json` adds three fields to check by hand, because all three fail silently: `repository.url` and `homepage` (a wrong value breaks installation with no build-time signal) and `strict_max_version` (blocks loading with no console output at all).

## Commits and branches

Commit messages follow `type(scope)!: description #issue`. `type` is required and must be one of `feat`, `fix`, `improve`, `hotfix`, `chore`, `docs`, `test`; `scope` is optional but worth having; `!` marks a breaking change; the trailing issue reference is optional. The `commit-msg` hook enforces this via commitlint, and the release notes are generated by grouping commits on it, so a message that doesn't parse falls through as an ungrouped line.

Branches are named `feat/*`, `fix/*`, `improve/*`, `hotfix/*`, or `release/*`.

Pull request titles follow the same convention as commits. The [PR template](./.github/PULL_REQUEST_TEMPLATE.md) asks what, why, and how, plus the verification checklist above.

## Documentation

Docs are organized along [Diataxis](https://diataxis.fr/) in [`docs/`](./docs/): `user-guide/` for end users, `contributing/` for development, `internals/` for how the plugin is built. User-facing behaviour changes belong in `user-guide/`; a constraint you had to discover the hard way belongs in `internals/`, where the next person will look for it.

```sh
npm run docs:dev      # local server with hot reload
npm run docs:build    # production build, fails on any dead link
```

Run `docs:build` after editing docs. Dead links fail the build, and prose references to a renamed file break without any signal at all.
