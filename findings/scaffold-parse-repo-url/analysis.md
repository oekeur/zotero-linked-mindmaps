# parseRepoUrl rejects valid repository URLs and mis-parses others

**Repo:** `zotero-plugin-dev/zotero-plugin-scaffold`
**Location:** `src/utils/string.ts:42-54`, consumed at `src/config.ts:41`
**Evidence:** reproduced against installed 0.8.8; regex identical at upstream HEAD
**Severity:** blocks every scaffold command, including a purely local `build`

## What the code does

```ts
export function parseRepoUrl(url?: string): { owner: string; repo: string } {
  if (!url) throw new Error("Parse repository URL failed.");

  const match = url.match(/:\/\/.+com\/([^/]+)\/([^.]+)\.git$/);
  if (!match) {
    throw new Error("Parse repository URL failed.");
  }
  const [, owner, repo] = match;
  return { owner, repo };
}
```

`resolveConfig` calls it during config load, so it runs for `build`, `serve`,
`test` and `release` alike. `owner` and `repo` feed the default `updateURL` and
`xpiDownloadLink` templates (`src/config.ts:95-96`) and the release target
(`src/config.ts:158`).

## Three separate defects

**1. The regex rejects ordinary repository URLs.** It requires all of: a `://`
scheme separator, a host whose last label is `com`, and a path ending in
`.git` whose repo segment contains no dot. That excludes:

- SSH remotes (`git@github.com:owner/repo.git`), the form `git clone` over SSH
  leaves in `package.json` when generated by `npm init` from an SSH remote
- any host not ending in `.com`: `gitlab.org`, `codeberg.org`, self-hosted
  `git.example.dev`
- URLs without the `.git` suffix, which is what GitHub's own "Code" button
  copies and what npm writes for many packages
- repo names containing a dot, which is common (`foo.js`, `my.plugin`)
- a trailing slash

**2. It silently mis-parses nested paths.** `[^/]+` for owner and `[^.]+` for
repo let the repo group span a slash, so a GitLab subgroup URL
`https://gitlab.com/group/subgroup/repo.git` returns
`owner=group, repo=subgroup/repo`. No error. That malformed repo name then
flows into `updateURL`, `xpiDownloadLink` and the release target, producing
broken URLs in a shipped `update.json`.

**3. The error message identifies nothing.** Both throw sites use the same
string, `"Parse repository URL failed."`, which names neither the offending
field (`package.json#repository.url`), nor its value, nor the expected format.
The stack lands in bundled scaffold code inside `node_modules`. A plugin author
running `npm run build` for the first time gets no path to the fix. This
project lost time to it during scaffolding, which is why the workaround is
recorded in this repo's CLAUDE.md rather than inferred from an error message.

## Adjacent issue worth noting in the same PR

For a repo that does parse, the default templates hardcode the host:

```ts
xpiDownloadLink: "https://github.com/{{owner}}/{{repo}}/releases/download/v{{version}}/{{xpiName}}.xpi",
updateURL: "https://github.com/{{owner}}/{{repo}}/releases/download/release/{{updateJson}}",
```

So a `gitlab.com` repository parses successfully and then gets `github.com`
update URLs. Overridable in config, but wrong by default and silent.

## Suggested fix

Replace the regex with `hosted-git-info`, which handles SSH, `git+https`,
shorthand and trailing-`.git` variants, and exposes the host so the default
templates can branch on it. Keep a regex fallback if adding a dependency is
unwelcome, but at minimum:

- accept SSH and scp-like forms, optional `.git`, any TLD, dots in repo names
- anchor the repo segment so it cannot span a slash
- name the field, the value found, and the expected shape in the error

## Why this matters more than its size suggests

It is the first error a new plugin author can hit, on the first command they
run, with no actionable text, in a file they did not write.
